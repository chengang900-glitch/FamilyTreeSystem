# 家谱管理系统（Web 版）产品开发方案

版本：v1.1（已确认，进入开发）
日期：2026-10-18（v1.0）／2026-10-18 修订（v1.1：确认决策、补公网安全设计与系统设置页规格）
目标：将本机已安装的桌面版「家族谱系管理系统 FamilyTreeSystem v0.0.4」克隆为 **Web 版**，并新增用户权限体系与移动端 H5 支持。

## 一、原型产品还原结论

### 1.1 原型技术栈（实测还原，非推测）

| 层级 | 原型实际方案 | 证据来源 |
|---|---|---|
| 后端 | Python 3.13 + Flask 3.1.3 + Werkzeug 3.1.9 + 原生 sqlite3 | 响应头 `Server: Werkzeug/3.1.9 Python/3.13.14`；`_MEI` 解压目录 dist-info |
| 前端 | Vite 构建 + React + Ant Design 5（单页 SPA，产物在 `frontend/`） | `/assets/index-*.js`、`vendor-react`、`vendor-antd` |
| 存储 | 每个项目一个独立 SQLite 文件 `projects/<项目名>/family_tree_data.db` | `C:\Users\1\Desktop\projects\刘氏家谱\` |
| 配置 | `config.yaml`（server/log/backup/import/export/ui/pedigree 六大段） | 桌面 `config.yaml` 全文 |
| 依赖 | lxml、Pillow、python-docx、PyYAML、pywin32 | `_MEI` 目录 |
| 世系树 | 自研 SVG 布局，**未使用** d3 / reactflow / G6 / antv | 前端 bundle 全量检索无命中 |
| 打包 | PyInstaller 单文件 exe，运行即启 Flask 本地服务（127.0.0.1:5000） | `_MEI000037002` 临时目录 |

关键判断：**原型本质是「单用户桌面软件套了一个浏览器壳」**——无用户表、无登录、无鉴权、无多租户隔离。Web 化的核心工作量不在"克隆功能"，而在"补上账号体系与数据隔离"。

| 模块 | 功能点 | 数据载体 |

### 1.3 原型数据模型（完整，8 张业务表 + 1 张元数据表）

| 表 | 关键字段 | 约束要点 |
|---|---|---|
| `person` | generation, name, courtesy_name, art_name, type(1-6), birth_date, birth_place, death_date, bury_address, record, notes, branch_id | generation>0；type 1-6 |
| `marriage` | spouse1_id, spouse2_id, marriage_order, marriage_date, divorce_date, marriage_place | 双方不同人；离婚≥结婚 |
| `parentchild` | parent_id, child_id, type(1-7) | 父子不同人 |
| `event` | name, time, place, type(1-2), branch_id | |
| `eventperson` | event_id, person_id, role | UNIQUE(event_id, person_id) |
| `branch` | parent_id, name, origin_place, hall_name, generation_chars, description | 自引用树 |
| `resource` | name, fid(UNIQUE), type(1-7), storage_path, file_size, mime_type | |

迁移策略：**8 张业务表字段与约束原样保留**，仅增加 `family_id` 列与索引，确保原型导出的 ZUP/JSON 可直接导入新系统。

## 二、新增需求：用户权限体系

### 2.1 角色定义

| 角色 | 作用域 | 说明 |
|---|---|---|
| `super_admin` 超级管理员 | 全系统 | 系统唯一/少数；管理所有用户、所有家谱；可创建/删除家谱、指派家谱管理员、改任意数据 |
| `family_admin` 家谱管理员 | 单个家谱（**可多个**） | 拥有本家谱全部编辑权限；可管理本谱成员名单（增删普通用户）、导出、备份、查看本谱操作日志 |
| `family_member` 家族普通用户 | 单个家谱 | 登录后仅可**查看**其所属家谱的全部内容（只读） |
| 未登录/游客 | — | 仅登录页（默认不开放公开只读，见 §9 待确认项 4） |

设计要点：超级管理员身份用 `users.is_superuser` 全局标志表示；家谱级角色统一落在 `family_members.role`，避免"两套角色表"带来的判定分叉。

### 2.2 权限矩阵

| 能力 | 超级管理员 | 家谱管理员 | 家族普通用户 |
|---|---|---|---|
| 用户管理（建档/启用停用/重置密码/改全局角色） | 全部 | 无 | 无 |
| 创建 / 删除 / 归档家谱 | 是 | 否 | 否 |
| 指派 / 取消家谱管理员 | 是 | 否 | 否 |
| 本谱成员名单管理（添加/移除普通用户） | 是 | 是 | 否 |
| 家谱元数据（堂号、字辈、修辑者、可见性） | 是 | 是 | 只读 |
| 成员 / 婚姻 / 亲子 / 事件 / 资源 / 分支 查看 | 是 | 是 | 是 |
| 上述模块 新增 / 编辑 / 删除 | 是 | 是 | 否 |
| 分支批量归人、批量操作 | 是 | 是 | 否 |
| 数据导入（JSON/GEDCOM/ZIP） | 是 | 是 | 否 |
| 数据导出（JSON/CSV/GEDCOM/ZUP） | 是 | 是 | 是（含资源文件包？建议仅数据，见 §9 待确认项 5） |
| PDF / Word 族谱导出 | 是 | 是 | 是 |
| 世系树导出图片 | 是 | 是 | 是 |
| 数据备份 / 恢复 | 是 | 是 | 否 |
| 操作日志 | 全部家谱 | 本家谱 | 无 |
| 系统配置（config.yaml 类） | 是 | 否 | 否 |

### 2.3 鉴权实现（后端强制，不依赖前端隐藏按钮）

1. 登录：账号密码 → 校验 `password_hash`（Werkzeug `generate_password_hash`，默认 scrypt）→ 签发 JWT（PyJWT，有效期 8h，刷新令牌 7d）；JWT 存 httpOnly Cookie，前端不落地 token。
2. 三层装饰器/依赖：
   - `@login_required`：解析 JWT，注入 `current_user`
   - `@super_admin_required`：`is_superuser == 1`
   - `@family_role_required(family_id, min_role=("admin"|"member"))`：查 `family_members` 判定
3. **越权防护（IDOR）**：所有业务接口路径强制 `/api/families/<fid>/...`，写操作二次校验目标记录 `family_id == fid` 方可执行；资源文件下载走 `/api/files/<resource_id>` 鉴权代理，禁止静态目录直链。
4. 审计：写操作统一写入 `operation_log`（操作人、家谱、动作、目标类型/ID、变更摘要 JSON、IP、时间），详情页可回看"谁改的"。
5. 防暴破：登录失败 5 次锁定 10 分钟；接口级速率限制（Flask-Limiter，可选）。

### 2.4 新增数据表

```sql
-- 用户
CREATE TABLE users (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  username TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  real_name TEXT,
  phone TEXT, email TEXT,
  status INTEGER NOT NULL DEFAULT 1,        -- 1 启用 / 0 停用
  is_superuser INTEGER NOT NULL DEFAULT 0,  -- 超级管理员
  must_change_pwd INTEGER NOT NULL DEFAULT 0,
  last_login_at TEXT,
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);

-- 家谱（由原 project 目录 + project_meta 升级而来）
CREATE TABLE family (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  slug TEXT NOT NULL UNIQUE,                -- 英文/拼音标识，用于资源目录名
  surname TEXT, hall_name TEXT,
  generation_chars TEXT, generation_frozen INTEGER NOT NULL DEFAULT 0,
  origin_place TEXT, description TEXT,
  visibility INTEGER NOT NULL DEFAULT 0,    -- 0 仅成员 / 1 登录可见 / 2 公开只读
  status INTEGER NOT NULL DEFAULT 1,        -- 1 正常 / 0 归档
  created_by INTEGER, created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);

-- 家谱成员与角色（多对多）
CREATE TABLE family_members (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  family_id INTEGER NOT NULL,
  user_id INTEGER NOT NULL,
  role TEXT NOT NULL CHECK (role IN ('admin','member')),
  granted_by INTEGER, granted_at TEXT NOT NULL,
  UNIQUE(family_id, user_id)
);

-- 操作日志
CREATE TABLE operation_log (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER, family_id INTEGER,
  action TEXT NOT NULL, target_type TEXT, target_id INTEGER,
  detail TEXT, ip TEXT, created_at TEXT NOT NULL
);

CREATE INDEX idx_family_members_user ON family_members(user_id);
CREATE INDEX idx_operation_log_family ON operation_log(family_id, created_at);
```

业务表改造（8 张表统一）：

```sql
ALTER TABLE person  ADD COLUMN family_id INTEGER NOT NULL DEFAULT 0;
-- 其余 7 张表同样处理
CREATE INDEX idx_person_family ON person(family_id);
```

## 三、技术栈推荐

### 3.1 推荐方案（方案 A）

| 层 | 选型 | 理由 |
|---|---|---|
| 后端运行时 | Python 3.13 | 与原型一致，团队无迁移成本 |
| Web 框架 | Flask 3.1 + Blueprint（auth / admin / family / pedigree / io / files） | 原型同款，最简；无需异步 |
| 数据库 | SQLite（WAL 模式，单库集中 `data/app.db`） | 家谱数据规模小（单谱通常 ≤ 10 万行）、写并发极低；零运维、备份即拷文件 |
| 数据访问 | 原生 `sqlite3` + 薄 Repository 层（原型风格） | 依赖最少；若未来迁 Postgres，仅替换 Repository 实现 |
| 鉴权 | PyJWT + Werkzeug `security` 密码哈希 + httpOnly Cookie | 依赖少，够用 |
| 配置 | PyYAML `config.yaml`（沿用原型结构） | 一致 |
| Word 导出 | python-docx | 原型同款，输出可编辑 .docx |
| PDF 导出 | **ReportLab**（纯 Python，嵌入 Noto Serif CJK 中文字体） | 跨平台；原型依赖 pywin32/Word COM，**Linux 部署不可用**，必须替换 |
| 图片/其它 | Pillow（缩略图）、lxml（GEDCOM/XML） | 原型同款 |
| 前端构建 | Vite + React 19 + **TypeScript** + Ant Design 5 + React Router | 原型 UI 已在 React/antd 上实现，克隆成本最低；TS 保障权限模型字段安全 |
| 状态管理 | Zustand（仅 auth / currentFamily 两个 store） | 比 Redux 轻；避免引入过多概念 |
| 世系树 | **自研 SVG + React**（树形/环状/扇形/直系延展/并排 5 种布局） | 原型即自研，无第三方图库依赖，可平移；SVG 天然支持导出 PNG/JPG/SVG |
| 移动端 | 同一前端工程响应式适配（断点 + 移动组件） | 一套代码，避免双端重复开发 |
| 部署 | Waitress（Windows）/ Gunicorn（Linux）+ 可选 Nginx；`docker-compose` 可选 | 单进程即可 |

### 3.2 备选方案对比

| 维度 | 方案 A：Flask + React/antd（推荐） | 方案 B：FastAPI + Jinja2 + HTMX + Tailwind | 方案 C：Next.js 全栈 + Postgres + Prisma |
|---|---|---|---|
| 依赖/构建复杂度 | 中（需 Node 构建前端） | **低**（无构建步骤） | 高 |
| 世系树交互实现 | 好（React 组件化 + SVG） | 差（手势缩放、5 种布局成本高） | 好 |
| 原型 UI 复用 | **高**（同为 React/antd） | 低（UI 全部重写） | 中 |
| 权限模型类型安全 | 好（TS） | 一般 | 好 |
| 部署运维 | 简单（单进程） | **最简单** | 较重（需 DB 服务） |
| 结论 | **推荐** | 仅当"坚决不要 Node 构建"时选 | 过度设计，不推荐 |

取舍说明：方案 A 的额外成本是保留一条前端构建链；收益是原型 UI/交互可近乎平移、世系树与批量选人等复杂交互可控。方案 B 虽然最简，但世系树与多实体关联表单的实现成本会反超。

### 4.2 API 设计（节选）

统一响应：`{ "code": 0, "msg": "ok", "data": {...} }`；`code` 401 未登录 / 403 无权限 / 4xx 业务错误。

| 分组 | 方法 | 路径 | 权限 |
|---|---|---|---|
| 认证 | POST | `/api/auth/login` `/api/auth/logout` | 公开 / 登录 |
| 认证 | GET/PUT | `/api/auth/me` `/api/auth/password` | 登录 |
| 超管 | GET/POST/PUT/DELETE | `/api/admin/users[/:id]` | super_admin |
| 超管 | GET/POST/DELETE | `/api/admin/families[/:id]` | super_admin |
| 家谱 | GET/PUT | `/api/families/:fid` `/api/families/:fid/meta` | member+ / admin+ |
| 家谱 | GET/POST/DELETE | `/api/families/:fid/members`（成员名单与角色） | admin+ |
| 业务 | GET/POST/PUT/DELETE | `/api/families/:fid/persons[/:id]` | 读 member+ / 写 admin+ |
| 业务 | 同上 | `.../marriages` `.../parentchild` `.../events` `.../branches` | 同上 |
| 资源 | POST/GET/DELETE | `/api/families/:fid/resources[/:id]` | 同上 |
| 资源 | GET | `/api/files/:resource_id`（鉴权后流式返回） | member+（且属本谱） |
| 世系 | GET | `/api/families/:fid/pedigree?root=&layout=` | member+ |
| 交换 | POST/GET | `/api/families/:fid/import` `/export` | 导入 admin+ / 导出 member+ |
| 付印 | POST | `/api/families/:fid/print/pdf` `/print/docx` | member+ |
| 日志 | GET | `/api/families/:fid/logs` | admin+（超管可跨谱） |

## 五、移动端 H5 适配方案

原则：**一套前端，两套布局容器**——不做独立 H5 工程，避免功能双写与版本漂移。

| 适配项 | 桌面（≥768px） | 移动（<768px） |
|---|---|---|
| 导航 | 左侧栏 + 顶部菜单 | 底部 TabBar（家谱 / 成员 / 世系树 / 我的）+ 顶部搜索吸顶 |
| 列表 | antd Table + 列设置 + 分页 | 卡片流（头像/世代/分支摘要）+ 无限滚动 + 下拉刷新 |
| 表单 | Modal 弹窗 | 底部 Drawer 全高抽屉，单列排布，大按钮 |
| 世系树 | 鼠标滚轮缩放 + 拖拽平移 | 双指捏合缩放 + 单指拖动；点击节点弹底部详情层；"适应"按钮常驻 |
| 批量操作（批量归分支、批量选人） | 完整支持 | 隐藏，提示"请在电脑端操作" |
| 文件上传 | 拖拽 + 选择 | `<input capture="environment">` 支持拍照直传；显示上传进度 |
| 布局细节 | — | `viewport` + `env(safe-area-inset-bottom)` 安全区；用 `dvh` 避免 iOS 地址栏遮挡；点击态去 300ms 延迟 |
| 性能 | 分页 50 | 分页 20 + 图片懒加载 + 长列表虚拟滚动 |
| 离线/PWA | — | 二期可选：manifest + Service Worker 缓存静态资源 |

移动端功能覆盖（一期）：登录、家谱切换、成员检索与详情、世系树浏览、资源查看、个人资料/改密、PDF 导出（跳浏览器下载）。
移动端不覆盖：批量选人、导入、备份恢复、用户与角色管理（超管后台）。

## 六、功能清单与优先级

| 优先级 | 模块 | 范围 |
|---|---|---|
| P0 | 基础框架 | 后端骨架、DB schema、配置、统一响应与错误处理 |
| P0 | 认证与权限 | 登录登出、JWT、三级鉴权、越权校验、审计日志、用户/家谱/角色管理后台 |
| P0 | 家谱与成员 CRUD | 家谱元数据、成员、婚姻、亲子 |

## 八、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 原型 PDF 依赖 pywin32 + Word COM | Linux/服务器不可用 | 改用 ReportLab 纯 Python 渲染，嵌入 Noto Serif CJK；封面竖排逐字定位 |

## 十一、部署方案：Linux 与 Docker

### 11.1 跨平台可行性

| 组件 | Windows | Linux | 说明 |
|---|---|---|---|
| Flask 3.1 / SQLite / PyJWT / PyYAML | 支持 | 支持 | 纯 Python |
| ReportLab（PDF） | 支持 | 支持 | 纯 Python，无系统依赖；**原型依赖的 pywin32 + Word COM 已在方案 A 中移除** |
| python-docx（Word） | 支持 | 支持 | 纯 Python |
| Pillow / lxml | 支持 | 支持 | Linux 主流发行版有预编译 wheel，免编译 |
| Waitress（WSGI） | 支持 | 支持 | Windows 首选 |
| Gunicorn（WSGI） | 不支持 | **支持** | Linux 首选生产服务器 |
| 前端构建产物 | 支持 | 支持 | 构建后为纯静态文件 |

结论：**方案 A 完整支持 Linux 部署**，无 Windows 专有依赖。

### 11.2 Docker 部署（推荐交付形态）

两阶段构建：Node 阶段构建前端，运行时镜像只承载 Python 服务与静态产物，不含 Node 工具链。

```dockerfile
# 阶段一：构建前端
FROM node:22-alpine AS web
WORKDIR /web
COPY web/package*.json ./
RUN npm ci --registry=https://registry.npmmirror.com
COPY web/ ./
RUN npm run build

# 阶段二：运行时
FROM python:3.13-slim
ENV TZ=Asia/Shanghai PYTHONUNBUFFERED=1
WORKDIR /app
COPY server/requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt
COPY server/ ./
COPY --from=web /web/dist/ ./webroot/
COPY fonts/NotoSerifCJKsc-Regular.otf /usr/share/fonts/
VOLUME ["/app/data"]
EXPOSE 8000
CMD ["gunicorn", "-w", "2", "-k", "gthread", "--threads", "4", \
     "-b", "0.0.0.0:8000", "--timeout", "120", "app:app"]
```

`docker-compose.yml`（应用 + Nginx 反向代理与 TLS 终止）：

```yaml
services:
  app:
    build: .
    volumes:
      - appdata:/app/data
    environment:
      - FTS_CONFIG=/app/data/config.yaml
    restart: unless-stopped
  nginx:
    image: nginx:1.27-alpine
    ports: ["80:80", "443:443"]
    volumes:
      - ./deploy/nginx.conf:/etc/nginx/conf.d/default.conf:ro
      - ./deploy/certs:/etc/nginx/certs:ro
    depends_on: [app]
volumes:
  appdata:
```

### 11.3 Linux / Docker 部署的关键约束

| 约束 | 风险 | 对策 |
|---|---|---|
| SQLite 数据持久化 | 容器重建导致数据丢失 | 必须挂载命名卷 `/app/data`（含 `app.db` 与 `uploads/`） |
| SQLite 与网络存储 | NFS/Ceph 上文件锁不可靠，可能损坏库 | 数据卷使用本地磁盘或块存储，禁止放 NFS |
| Gunicorn 多进程写冲突 | `database is locked` | SQLite 启用 WAL + `busy_timeout=5000`；worker 数不超过 2；家谱场景写少读多可接受 |
| 中文字体 | PDF 中文变方块 | 镜像内预置 Noto Serif CJK（SIL OFL），配置中登记字体路径 |
| 时区 | 时间戳与备份命名差 8 小时 | 容器设 `TZ=Asia/Shanghai`，应用内时间统一按 UTC+8 存储 |
| 上传目录权限 | 非 root 用户无法写入 | 启动时修正数据卷属主，或固定 uid/gid |
| 反向代理 | 真实 IP 丢失、大文件上传失败 | Nginx 传 `X-Forwarded-For` / `X-Forwarded-Proto`，调大 `client_max_body_size` |
| TLS | 明文传输 | Nginx 终止 TLS（Let's Encrypt），应用侧开启 HSTS |

### 11.4 何时需要换 PostgreSQL

SQLite 适用于：家谱数不超过数百、单谱成员不超过数万、并发写极低（修谱本质是低频录入）。
出现以下任一情况建议迁移：持续并发写 QPS 大于 10、需要多机横向扩展、单库超过 2GB。
数据访问已收敛在 `db/repo/` 层，切换只需替换 Repository 实现，业务代码不动。

## 十二、互联网部署安全设计

| 类别 | 措施 |
|---|---|
| 传输 | 全站 HTTPS；HSTS `max-age=31536000`；Nginx 终止 TLS |
| 会话 | JWT 存 httpOnly + Secure + SameSite=Strict Cookie；访问令牌 8 小时、刷新令牌 7 天；登出即失效 |
| CSRF | SameSite=Strict + 写接口校验 Origin / Referer 白名单 + 自定义请求头 |
| XSS | 富文本输出转义；CSP 限制脚本来源 |
| 注入 | 全部参数化查询，禁止拼接 SQL |
| 暴破 | 登录失败 5 次锁定 10 分钟；单 IP 速率限制；首登强制改密 |
| 密码 | Werkzeug scrypt 哈希；长度与复杂度策略可在系统设置调整 |
| 文件上传 | 类型白名单、大小上限、随机文件名、存储于非 Web 根目录、下载走鉴权代理 |
| 越权 | 接口按 `family_id` 作用域校验；写操作二次校验记录归属；资源下载鉴权 |
| 审计 | 写操作全量入 `operation_log`；记录登录失败 |
| 错误处理 | 生产关闭调试栈；统一错误码；不泄露路径与 SQL |
| 备份 | 定时 `sqlite3 backup` + 资源目录打包，保留 N 份 |
