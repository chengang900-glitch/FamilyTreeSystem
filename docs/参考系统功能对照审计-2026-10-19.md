# 参考系统功能对照审计

日期：2026-10-19。

本文件保留初次审计结论；后续修复与用户新增反馈的完成状态见[参考功能完善说明](参考功能完善说明-2026-10-19.md)。

参考：[ckyim《家族谱系管理系统（FamilyTreeSystem）》](https://www.bilibili.com/opus/1248278128044802080)，页面标注编辑于 2026-10-15。本次已读取文章正文；文章的功能说明作为对照基线，不代表已实际运行参考软件。

项目范围：当前工作目录中的 `server/`、`web/src/`，包含已有的未提交修改。本次未修改业务代码、现有文档或运行数据库，仅新增本报告。旧文档作为线索，最终结论以当前源码和隔离样例为准。

## 结论

文章涉及的 11 个主要模块均已有对应实现，没有发现某个主要业务模块整体缺失。但“模块存在”不能等同于“已经完整复刻”。

本次发现 13 项明确缺口或不完整实现，集中于亲子批量录入、分支批量归人、完整世系展示、数据交换完整性及付印质量。另有参考软件数据格式兼容性尚未验证。

## 一、11 个模块对照

| 参考模块 | 当前项目 | 判断 |
|---|---|---|
| 项目/家谱 | 多谱新建、选择、切换与权限隔离 | 主体已实现；缺少最近访问列表；从独立项目库改为共享库按家谱隔离 |
| 族人档案 | 世代、姓名字号、六类成员、生卒地点、生平、备注与分支 | 基本字段已覆盖；日期为自由文本 |
| 婚姻 | 双方、次序、结婚/离婚日期、地点及说明 | 主要字段和增删改已覆盖 |
| 亲子 | 关系维护、七种类型、多子女登记、列表/卡片 | 只能一次选一位父/母，不能逐个子女配置与双方的关系 |
| 家族事件 | 时间、地点、分支、描述、参与人和角色 | 主要能力已覆盖；参与人通过保存后的独立面板维护 |
| 文献资源 | 七类资源、上传下载、大小/路径、五类实体关联 | 主体已实现；大数据量关联选择不完整 |
| 分支房系 | 层级、发源地、堂号、字辈、家训、成员归属 | 主体已实现；批量接口存在，页面仍逐人操作 |
| 世系树 | 五种布局、直系过滤、适应、缩放、三种图片导出 | 入口齐全，但两个布局可漏成员，SVG 边距未生效 |
| 数据导出 | 九模块选择、JSON/CSV/GEDCOM/ZUP、资源打包 | CSV 漏资源关联；GEDCOM 只保留部分信息 |
| 数据导入 | JSON/GEDCOM/ZIP/ZUP、关系 ID 重映射、资源写回 | 本系统格式有实现；项目元数据未在普通导入中应用，参考包未验收 |
| PDF/Word 付印 | 三步操作、模式、内容开关、封面、页数估算、四种纸张 | 已能生成文件，但纸张、世代深度、正文排版仍有明显缺口 |

浅色/深色主题，以及成员、婚姻、亲子、事件、资源、分支的列表/卡片切换，当前源码均已具备，不应继续列为未实现。

## 二、未实现或实现不完整的具体项目

状态说明：“未实现”指缺少所述能力；“部分实现”指已有对应模块或接口但不完整；“已复现缺陷”指隔离样例执行确认了错误行为。P1 优先解决结果正确性与数据完整性，P2 补齐操作能力，P3 为便利性。

### 1. 父母与多子女同屏、逐个设置生养关系

- **状态：部分实现，P2。**
- 当前表单是一个 `parent_id`、一组 `child_ids` 和统一 `type`，后端对所有子女应用同一个类型。
- 无法一次同时登记父亲、母亲，也无法在同一次操作中给不同子女设置不同的父子/母子关系。
- 代码：[ParentChild.tsx](../web/src/pages/ParentChild.tsx#L168)、[family_bp.py](../server/blueprint/family_bp.py#L535)。
- 验收建议：同屏登记父母与两名子女，为每个子女分别指定与父、母的关系，保存后逐条核对。

### 2. 分支成员批量选择、全选及类型/世代筛选

- **状态：页面未实现，后端具备批量接口，P2。**
- 页面用单值 `addId`，每次提交 `add_ids: [addId]`，移出同样逐人操作。
- 没有参考页面中的勾选、多选、全选/取消及类型/世代筛选，也不能新建分支时一并选择成员。
- 代码：[Branches.tsx](../web/src/pages/Branches.tsx#L129)、[family_bp.py](../server/blueprint/family_bp.py#L775)。
- 验收建议：按世代/类型筛选并一次加入、移出多名成员，检查未选成员归属不变。

### 3. 最近访问的家谱列表

- **状态：未实现，P3。**
- 当前只用 `localStorage.fts_family` 保存最后选择的一谱，没有访问历史及按最近使用排列的入口。
- 代码：[store.ts](../web/src/store.ts#L43)、[Home.tsx](../web/src/pages/Home.tsx#L6)。

### 4. 全族成员的完整世系展示

- **状态：已复现缺陷，P1。**
- 树形布局在有根节点时只从这个根沿子女向下绘制，不会补绘配偶、其他根节点或未连接成员。
- 直系延展布局只展开主链和主链节点的直接旁支，未继续展开旁支后代。
- 用“始祖、配偶、两个孩子、两个孙辈”的 6 人样例执行实际布局函数：树形绘出 5 人，漏配偶；直系延展绘出 4 人，漏配偶及一个旁支孙辈；另三种布局均绘出 6 人。此样例关闭了“只看直系”。
- 代码：[layout.ts](../web/src/pedigree/layout.ts#L78)、[layout.ts](../web/src/pedigree/layout.ts#L166)。
- 验收建议：包含夫妻、多根、旁支孙辈的样例，在全谱模式下核对预期成员集合，不能只核对布局菜单存在。

### 5. SVG 导出可调边距

- **状态：部分实现，P2。**
- PNG/JPG 用 `exportMargin` 扩大画布并平移图片，固定生成 2 倍分辨率；SVG 分支直接序列化原 SVG，没有应用这个边距。
- 导出还会克隆当前缩放/拖动变换，完整取景效果需要浏览器验证。
- 代码：[Pedigree.tsx](../web/src/pages/Pedigree.tsx#L114)。
- 验收建议：相同布局分别以 0 和 100px 边距导出三种格式；核对 SVG 的画布/viewBox 与留白确实改变。

### 6. CSV 九模块完整导出

- **状态：已复现缺陷，P1。**
- 页面提供“资源关联”模块，但 CSV 分支没有输出 `resource_relations.csv`。
- 构造一条真实资源关联后导出，全模块 ZIP 仍只有 8 个 CSV，缺少该关联表。
- 代码：[io_bp.py](../server/blueprint/io_bp.py#L205)。
- 验收建议：九模块逐个勾选导出，核对 CSV 文件与记录，特别检查同一文献关联多实体的关系。

### 7. 普通 JSON/ZIP 导入项目元数据

- **状态：已复现缺口，P1。**
- 导出包含 `family`，但普通导入的 `_apply_json` 仅写业务表，不应用家谱名称、堂号、字辈、修辑者等项目元数据。
- 隔离样例中源谱含字辈“天地玄黄”、冻结为 1，导入目标谱后字辈仍为空、冻结仍为 0；人员和关系已正常导入。
- 家谱备份恢复接口有单独恢复元数据的逻辑，因此不能据此声称所有导入路径均已覆盖。
- 代码：[io_bp.py](../server/blueprint/io_bp.py#L569)、[io_bp.py](../server/blueprint/io_bp.py#L428)。
- 验收建议：明确追加/覆盖导入对项目元数据的规则，并验证名称、堂号、字辈、冻结状态、修辑者的结果。

### 8. GEDCOM 数据互通的字段完整性

- **状态：仅实现基本互通，P1。**
- 当前输出人物姓名、性别、生卒日期和基本家庭结构；未输出婚姻日期/地点等信息，解析器也没有读取婚姻事件的对应逻辑。
- 实际含“1950-01-01、杭州”的婚姻导出后，GEDCOM 没有 `MARR` 记录，也没有上述日期/地点。
- 字号、出生地、详细记事、亲生/收养类型等也没有对应的完整往返映射。不能将 GEDCOM 视为本系统完整备份格式。
- 文章宣称格式互通，但未给出其 GEDCOM 字段映射；这里确认的是本项目的信息保真边界，不能据此断言参考软件对每个字段均无损。
- 代码：[io_bp.py](../server/blueprint/io_bp.py#L98)、[io_bp.py](../server/blueprint/io_bp.py#L229)、[io_bp.py](../server/blueprint/io_bp.py#L760)。
- 验收建议：制定保留字段清单，至少验证婚姻日期/地点及亲子类型，并在导出前明确提示无法保留的信息。

### 9. Word 按所选纸张输出

- **状态：已复现缺陷，P1。**
- Word 分支直接创建默认 `Document()`，没有设置节的纸宽/纸高。
- 实际分别传入 A4、A5、16K、32K，解析生成 DOCX 的节属性，四次都是 **215.9 × 279.4mm**，即默认 Letter 尺寸。
- PDF 分支有调用 `paper_size()`，不能将此问题推广成 PDF 纸张也未实现。
- 代码：[print_bp.py](../server/blueprint/print_bp.py#L223)。
- 验收建议：直接检查四份 DOCX 的 `w:pgSz`，应分别对应 210×297、148×210、195×270、130×184mm。

### 10. 个人付印模式的世代深度

- **状态：已复现缺陷，P1。**
- 个人模式遍历全部后代，没有应用 `generations`；世系模式才进行深度截断。
- 用始祖→儿子→孙子的三代样例，调用个人模式且深度为 1，仍返回三代全部人物；世系模式的深度 1 则只返回第一世。
- 由于预估、PDF、Word 共用 `_load`，这一范围选择问题影响三条路径。
- 代码：[print_bp.py](../server/blueprint/print_bp.py#L48)。
- 验收建议：同一主人物分别选择全部、3/4/5 代，核对输出与预估的人物集合、起算世代。

### 11. 参考样式的族谱正文排版

- **状态：未达到参考样式，P2。**
- 参考文章展示按世代分栏、妻/子/女区分的正文。当前是“世代标题＋人物＋若干说明”的顺序文本；PDF 封面已有竖排标题，正文没有分栏。
- 子女全部使用“子：”标签，没有根据类型分别列子、女；Word 封面也使用普通标题排版。
- 这是输出样式和信息表达缺口，不应说成 PDF/Word 导出整体未实现。
- 代码：[print_bp.py](../server/blueprint/print_bp.py#L79)、[print_bp.py](../server/blueprint/print_bp.py#L144)、[print_bp.py](../server/blueprint/print_bp.py#L223)。
- 验收建议：用包含多代、多配偶、儿女与长记事的固定样例，同页对比参考图和实际文件。

### 12. 长篇内容的 PDF 换行与分页

- **状态：代码确认缺少长文本排版，视觉结果待验证，P1。**
- PDF 对生平记事等文本直接调用 `drawString`，未按可用宽度折行；页数估算也按一条记事一行计高。
- 据此判断长文本存在越过纸张边界、预估失真的风险；本次未生成并渲染长文 PDF，不能报告为已完成视觉复现。
- 代码：[print_bp.py](../server/blueprint/print_bp.py#L116)、[print_bp.py](../server/blueprint/print_bp.py#L206)。
- 验收建议：A5/32 开分别输出千字生平，核对右边界、续页和预估页数。

### 13. 大谱文献关联对象选择

- **状态：部分实现，P2。**
- 文献可关联五类实体，但选择框只请求 `?size=200` 的第一页，并在已返回的数据中本地搜索。
- 超过首批 200 条的对象没有继续分页或远程搜索入口，影响“同一份文献可关联成员/婚姻/亲子/事件/分支”的大谱使用。
- 代码：[Resources.tsx](../web/src/pages/Resources.tsx#L126)。
- 验收建议：每类建立超过 200 条对象，搜索并关联末尾对象，验证关系保存。

## 三、不能直接当作缺失功能的项目

1. **冻结字辈已实现。** 超管家谱设置有开关；后端新建分支时会在开启冻结且未填写覆盖值时沿用家谱字辈。本次隔离样例已验证沿用“天地玄黄”。不过它位于家谱全局设置，与参考文章的分支录入操作位置不同，家谱管理员也缺少对应的元数据编辑页。不能写成完全没有冻结功能。
2. **农历/公历目前可作为文本同时记载。** 一个生卒日期字段可以存“农历描述（公历日期）”，但没有结构化双日期、农历解析或互转。参考文章并未明确承诺自动换算，不能将自动互转当作已确认的原版功能。
3. **一谱一独立数据库与 Windows 单文件程序，是架构/交付差异。** 当前方案选择 Web 多用户、共享 SQLite 按 `family_id` 隔离；可本机部署，但没有参考软件那种双击单文件的交付形式。是否补齐应由部署目标决定。
4. **CSV 导入不是本次确认的缺口。** 文章的导入范围列为 JSON/GEDCOM/ZIP，不能仅凭“Excel 可编辑”推出必须支持 CSV 导回。
5. **公开只读、邀请码、PWA 不纳入这次缺口。** 参考文章没有提出这些能力，项目旧方案的二期项目不能自动算作参考系统未对齐项。

## 四、待确认：参考软件真实数据包兼容性

当前 JSON/ZUP 使用本系统的字段名、目录及资源文件命名约定；本系统自己导出再导入成功，只能证明自身闭环。

本次未取得参考软件实际导出的 JSON/ZIP 文件，不能确认原版数据是否可以直接导入，不能确认原版 ZIP 内资源目录/FID 命名是否一致。文章正文明确介绍 ZIP，项目文档另外提到 ZUP；不能仅凭扩展名相似就认定两者兼容。

验收应使用参考软件导出的匿名样例，至少包含分支、人员、婚姻、亲子、事件参与人、资源原件与关联，以及项目元数据，逐表、逐文件核对。

## 五、本次验证范围与建议顺序

已执行：

- 前端 `npm run typecheck` 通过。
- Node 直接执行当前 TypeScript 布局函数，对 6 人样例比较五种布局的节点集合。
- 临时 SQLite＋实际 Flask Blueprint 的隔离组件核验：Word 四种纸张、个人/世系深度、CSV 内容、GEDCOM 婚姻字段、JSON 导入元数据及关系、冻结字辈沿用。
- 核验身份由测试程序注入；未经过真实登录、应用中间件或部署服务，因此不代表鉴权/浏览器 E2E 通过。

未执行：

- 当前已部署服务的浏览器操作和移动端验收。
- 参考软件运行与真实数据包导入。
- PDF 文件生成、中文字体效果和长文本视觉检查。系统 Python 缺少 ReportLab/PyJWT，故本次采用不启动完整应用的组件核验；没有安装依赖或变更运行环境。
- 旧文档中全部 212 项测试的重跑。

建议顺序：先修世系漏人、CSV 关联遗漏、导入元数据规则和付印参数失效；再补长文本排版与 GEDCOM 保真；最后补父母同屏、分支批量、关联选择、SVG 边距、参考版式和最近访问。

旧《产品功能缺口清单》中将 M4 世系树、M6 付印整体标为已完成，粒度偏粗，不能覆盖本报告复现的缺陷；该旧文件本次保持不变。
